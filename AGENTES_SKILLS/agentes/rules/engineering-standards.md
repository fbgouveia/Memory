# �  PADRÕES DE ENGENHARIA SOBERANA (G:\)

> **Missão:** Combater o Vibe Coding e garantir a longevidade do Enxame (VLAEG).

## 1. DEFINITION OF DONE (DoD)
Um código só é considerado 'Pronto' (GSD) se:
- [ ] **Sem Alucinações:** Cada linha foi revisada e sua intenção é clara.
- [ ] **Nomes com Intenção:** Variáveis e funções descrevem *o que* fazem, não *o que* são (ex: calculateInvoiceTotal vs calc1).
- [ ] **Single Responsibility:** Cada função faz apenas uma coisa e faz bem.
- [ ] **Testabilidade:** O código permite ser testado de forma isolada (Injeção de Dependência).
- [ ] **Documentação Inline:** Comentários explicam o 'Porquê', não o 'Como' (o código deve explicar o 'Como').

## 2. ANTI-PATTERNS (PROIBIDOS)
- **Vibe Coding:** Copiar código sem entender o fluxo.
- **Underengineering:** 'Gambiarras' que ignoram a estrutura de dados correta.
- **Overengineering:** Criar 10 interfaces para um script de 5 linhas.
- **Hardcoding:** Valores 'mágicos' espalhados pelo código. Use constantes ou config.

## 3. RITUAL DE VALIDAÇÃO
1. **Analise:** O problema foi entendido profundamente?
2. **Arquitete:** O desenho da solução foi validado?
3. **Codifique:** O código segue o Clean Code?
4. **Audite:** Passe o 'Linter' e realize o 'Self-Review'.

## 4. PILARES DA SOBERANIA (CHECKLIST OBRIGATÓRIO)
Antes de cada 'GSD' em projetos em G:, realize a auto-auditoria:
- [ ] **Refatoração:** Este código possui 'cheiro' de débito técnico? Ele pode ser simplificado?
- [ ] **Escalabilidade:** Como este script se comporta com 10, 100 ou 1000 registros/usuários?
- [ ] **Performance:** Existe algum loop desnecessário ou consumo excessivo de memória?
- [ ] **Concorrência/Paralelismo:** O código é thread-safe? Existe risco de race conditions ou deadlocks?

## 5. O PODER DE VETO (ANTI-PAPAGAIO)
Se a IA (eu) sugerir um código, o Engenheiro (você) ou o Orquestrador (eu-v2) deve:
1.  Identificar a **procedência** da lógica (se ela é baseada em boas práticas ou 'alucinação').
2.  Validar se a lógica é a **mais simples** ou apenas a **mais fácil**.
3.  Rejeitar o código se ele for 'sujo' ou 'caótico'.

## 6. O CHECKLIST DO 'ZERO CÓDIGO' (GSD SOBERANO)
Antes de escrever QUALQUER nova função ou script:
1.  **Simplificação:** Existe um jeito de resolver sem novo código? (Processo, Configuração, Recurso Nativo).
2.  **Manutenibilidade:** Este código será uma dívida t�cnica ou um ativo em 5 anos?
3.  **Performance:** Qual a complexidade algorítmica (O(n)) desse plano?
4.  **Escalabilidade:** O que acontece se o volume de dados dobrar amanhã?
